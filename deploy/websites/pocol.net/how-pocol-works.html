How a PoCol block comes together

A mining round connects a shared template, deterministic work assignment, proof-of-work search and full validation. Each stage has a specific job; finding a low hash is only one part of producing an accepted block.

01 · Agree on the network

A GenesisSpec identifies the network through its chainId, consensus parameters, initial allocation, initial miner list and system-contract code hash. Nodes check this identity before accepting data. Before startup, ParamGate evaluates the profile against admission rules and refuses inconsistent configurations. Sharing a network name alone is not sufficient.

The initial miner set and parameters are part of that shared starting point. Changing them is a protocol or network-configuration decision, not an ordinary website setting.

02 · Establish the shared template

The selected proposer signs the first-attempt template, including its transactions, timestamp and target. Other miners validate that template before using it. If the proposer misses the allowed window, the rules supply a deterministic fallback with an empty transaction body. Later attempts use fallback rules as well, keeping the round lifecycle explicit.

03 · Assign and search

The parent block's seal, current height and attempt number determine a seed. Each eligible miner receives a ticket derived from that seed and its identity. Sorting the tickets gives the order for partitioning the nonce space. Each range is contiguous and separate from the others; its boundaries can be recomputed by other nodes.

Miners hash the template identifier together with a nonce. A result below the easier share target is a contribution; a result below the block target is a candidate solution. The implementation stops its search when it finds a solution, is cancelled or exhausts the assigned range. ASERT adjusts subsequent targets toward the configured block-time objective.

04 · Validate, select and continue

Nodes check encoding, identity, timing, difficulty, nonce ownership, signatures, shares, transaction limits and execution roots. An acceptable hash cannot override a failure in these checks. Valid competing branches are compared by cumulative work, with a defined tie-break. Reorganizations can change the selected history within the node's supported retention limits.

The next block records the previous block's winner and committed shares. Reward settlement follows later, so the current template does not depend on a winner that has not yet been found. Finality remains probabilistic; the documented confirmation labels are not a mathematical security guarantee.
