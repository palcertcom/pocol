What is implemented — and what remains open

PoCol is an experimental research implementation. This guide describes the repository at a specific revision and separates working development features from security objectives and production requirements that are not yet established.

Demonstrated in the development stack

The repository contains a Rust mining node, peer-to-peer synchronization, EVM execution, durable journals, system contracts, on-chain site publishing and a Chrome extension. Its recorded tests cover a three-node devnet, branch reorganization, restart recovery, verified website fetching and isolated browser rendering. Linux, Windows Server and Chrome verification are documented for particular revisions and environments.

These results establish the scope of those tests. They do not mean that every configuration, platform, failure mode or worst-case resource condition has been validated. A successful test suite is useful evidence, but its environment and exact source revision matter.

Production readiness is not claimed

The current README labels the code simnet-only and not production-ready. It states that the production network profile does not boot on pocold: an approved network genesis is absent, whole-state mode does not meet the stated A13 memory condition, and admission rules R21 and R22 remain blockers. The experimental on-disk state mode has a computed resource model, with some worst cases still unmeasured.

Use disposable development accounts and test assets when following repository walkthroughs. The documentation explicitly excludes real funds. Network activity visible in an explorer does not, by itself, establish a production security review or resolve these documented requirements.

Security objectives remain research questions

PoCol retains a PoW puzzle and cumulative-work selection, but PoW's security guarantees do not automatically transfer to its coordinated rules. Fairness, Sybil resistance and PoW-equivalent security are stated objectives rather than proven properties. The threat model discusses template withholding, identity splitting, share exclusion, clock assumptions and malicious RPC responses. No independent external human security audit has been completed.

Read the browser's trust boundary

The extension verifies website hashes and uses isolation controls, but its trust modes have different guarantees. RP checks network identity and a limited header window; it does not reexecute the full chain or prove complete EVM state. LN relies on a trusted local node. The trust banner outside the website frame tells the visitor which mode is in use. Treat these checks as specific protections, not a blanket promise that arbitrary website code is safe.
