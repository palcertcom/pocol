Smart contracts

PoCol pairs collaborative mining with an EVM execution layer. Mining determines which block the network accepts; contracts define what applications do with the transactions inside it.

Build in PoCol IDE

Write Solidity, compile your project and work with a deployed contract in one browser workspace. PoCol IDE includes starter contracts, file management, compiler diagnostics and an interaction panel generated from your contract ABI. Projects are stored in this browser; export a project ZIP to keep a backup.

Open PoCol IDE ↗See the IDE workspace

Your first contract: Counter

Use the local sandbox to learn the workflow before sending a network transaction. You do not need to connect a wallet or fund an account for this exercise.

  • Open the Counter starter in PoCol IDE. Edit Counter.sol, then select Compile. Resolve any errors and select the compiled contract.
  • Keep Local sandbox selected. In Deploy, set the initial value to 10 and deploy. In Interact, read count, call increment, then read count again: 11.

Deploy to PoCol Mainnet

Install PoCol Studio & Viewer 0.4.1, then refresh the IDE. Compile the current source, select PoCol Mainnet and use PoCol wallet as the signing path. Enter the constructor inputs and any value to send, then select Continue in PoCol wallet. The extension opens a separate confirmation tab where you unlock the wallet and review the account, network, deployment data and maximum fee in PCOL. Confirm only after reviewing that request.

Wait for the transaction receipt, then open Interact to read values or call functions. State changes require a new wallet approval. Follow the transaction in Explorer and export your project backup.

The extension includes tools/Export-Studio-Wallet.ps1 for Windows and tools/export-studio-wallet.py for Linux. Follow the included instructions to create an encrypted wallet export on your device. Import and unlock it only in the extension wallet tab. The IDE never asks for your private key or wallet password.

Local tests and network deployments

The sandbox runs Cancun EVM execution locally. It does not publish to PoCol or reproduce PoCol consensus and all network-specific limits. A PoCol Mainnet deployment is a separate transaction and needs an account with PCOL for fees.

Projects are saved in this browser on this site. Export a ZIP to keep a copy outside the browser or move to another device. The local sandbox is temporary: resetting it or reloading the page clears its deployed contracts and simulated balances.

From a transaction to a shared result

A contract is a program stored at a blockchain address. A transaction can deploy code, call a function or transfer value. Each node executes the block against the preceding state and checks the resulting commitments. Contract state and receipts become part of the block's verified result.

The implementation uses revm 19.7 with Cancun execution rules. Consensus and execution are separated: the execution layer receives the parent state, block context and transactions, then returns updated state, receipts and roots. This separation lets applications use familiar EVM concepts while PoCol organizes the mining work differently.

Familiar interfaces for applications

The node exposes a supported subset of Ethereum-style JSON-RPC. Applications can read balances and contract code, simulate a call, estimate gas, submit a signed transaction and inspect receipts or logs. A read simulation does not commit state or broadcast a transaction.

A contract address identifies the program; an account key authorizes the sender. Reading a value and changing that value are different operations: a state-changing action needs a signed transaction, gas and inclusion in an accepted block. Its receipt records whether execution succeeded.

  • Read and simulate: eth_getBalance, eth_getCode, eth_call and eth_estimateGas.
  • Submit and follow execution: eth_sendRawTransaction, eth_getTransactionReceipt and eth_getLogs.
  • Accepted transaction formats include EIP-155 legacy, EIP-2930 and EIP-1559, bound to the configured chain ID.

Contracts inside the protocol

PoCol also uses system contracts for miner registration, reward escrow, share accounting, chain caps and website chunks. Their privileged operations follow the block's execution phases. Applications cannot simply impersonate the system caller to perform those operations.

This gives collaborative mining an execution-layer record: work evidence and reward settlement are processed according to protocol rules, rather than being only an off-chain accounting promise.

Compatibility has a defined scope

EVM support does not mean that every Ethereum feature or tool works unchanged. PoCol applies additional limits to accounts, storage slots, code, transaction bytes and logs. Transaction types 3 and 4 are rejected, and the specification documents other differences. Developers should test their contracts on the supported local network and use the repository's current RPC and execution references.

The current implementation is experimental. EVM compatibility does not establish Ethereum-equivalent consensus security or production readiness.
